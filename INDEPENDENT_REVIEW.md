## 1. Executive summary

The implementation has a strong financial foundation: BCMath decimal strings, generation-specific rates, PostgreSQL constraints, stable provider idempotency keys, a durable webhook inbox, and row-locked settlement. Fresh verification found **111 passing tests, 353 assertions, zero failures and zero skips**. Production assets build successfully; Pint, PHPStan, frontend lint/format checks, and Vue type checking pass. Read-only calls to the real provider independently corroborated the existing successful/failed generations and exact usage reconciliation.

Green checks do not establish complete behavior. This review reproduced these defects without changing application code:

1. Valid long Unicode prompts receive estimates whose encrypted quotes the submission endpoint rejects.
2. Provider `Retry-After` can be shortened by a delayed processing snapshot or bypassed by manual retry after automatic retries are exhausted.
3. Lost webhook jobs older than 24 hours are permanently excluded from the recovery scan.
4. Account deletion promises permanent removal of all data while retaining generation prompts and related records.

The first three affect requested generation/reliability behavior. The fourth is a product/privacy inconsistency in an exposed feature. There are also test-quality and lower-priority UX issues. No critical security exploit, incorrect arithmetic, or duplicate charge was demonstrated. Public deployment, public repository delivery, and hosted acceptance remain incomplete by explicit user instruction; that is an outstanding submission gate, not unauthorized work this review should perform.

**Reviewer independence limitation:** the reviewing assistant also authored the earlier implementation. This is a fresh, skeptical audit with newly executed checks and counterexamples, but it is not an organizationally independent or non-author review. The filename was requested by the user and must not be interpreted as independent third-party certification.

**Change boundary:** only this report was added to the checkout. No source fixes, dependencies installed, commits, pushes, deployments, or new provider generations. Verification ran in a disposable copy inside the existing Sail application container. A separately owned PostgreSQL database was created and removed. Development business records were inspected within read-only transactions. Temporary diagnostic records were confined to the audit database and rolled back.

### Relevant API contract extracted

- Bearer authentication; environment-specific keys, signing secrets and usage reports. Request/concurrency/daily limits are account-wide across keys.
- Create returns 202; retrieve returns the generation snapshot. Allowed statuses are queued, processing, succeeded and failed; both terminal statuses are final.
- Prompt maximum 4,000 Unicode characters; three sizes and three quality levels; at most four HTTP(S) reference URLs. Metadata permits up to 20 string values of at most 500 characters. Unknown create parameters are rejected.
- Same account idempotency key plus identical parameters returns the existing generation, possibly already terminal; different parameters return 409. Keys never expire and are at most 255 characters. Replays do not consume an additional generation/concurrency allocation.
- Public pricing supplies current rates and token rules. Estimate text with Unicode character count, ceiling division and up to 15% variance; references, quality/size output tokens and maximum reasoning tokens also contribute. Rates must not be hardcoded in production calculations.
- Actual billing uses all four token categories and the generation's fixed rates. Provider amounts are exact decimal strings; usage reports use nine decimal places. Failed generations and rejected creates cost nothing. The application adds exactly 25%.
- Errors include 401 invalid key; 422 validation; 400 content rejection; 404 resource not found; 409 idempotency conflict; 429 rate, concurrency and daily limits; 503 overload. Respect Retry-After, back off and cap retries. Unknown outcomes require safe idempotent recovery.
- Limits: 60 authenticated requests/minute, three concurrent generations, 500 generations/UTC day. Headers advertise remaining request budget. The application need not reproduce the provider's quota enforcement, but must handle its responses.
- Webhooks carry full snapshots. Verify HMAC-SHA256 over timestamp plus the exact raw body, compare in constant time and reject stale timestamps. Events may duplicate, arrive out of order, arrive before create returns, or never arrive. The endpoint must acknowledge within ten seconds; provider retries have six attempts total. Polling is the documented fallback.
- Signed PNG URLs expire 24 hours after completion; retrieving again does not extend expiry. Persisting images is optional here.
- Usage is scoped to the called key, grouped by UTC completion date, includes zero days, accepts an inclusive range of at most 92 days, and includes exact cost totals.
- Test keywords: blocked, overloaded, fail, succeed, slow and duplicate. Slow means 60–90 seconds; duplicate means two deliveries per lifecycle event.

## 6. Medium and low-priority findings

### F01 — Medium: accepted valid prompts produce unusable encrypted quotes

**References:** `app/Http/Requests/GenerationRequest.php:18–23`; `app/Http/Controllers/GenerationEstimateController.php:24–33`; `app/Http/Controllers/GenerationController.php:40`; `resources/js/pages/Dashboard.vue:188`; `tests/Unit/PricingCalculatorBoundaryTest.php:5–10`; `tests/Feature/GenerationControllerTest.php:119–134`.

**Impact:** users can review a valid price but cannot generate. JSON's default Unicode escaping, encryption and base64 expansion make the opaque quote longer than the submission validator permits. This is not a malformed/tampered quote. Refreshing the estimate does not repair it.

**Reproduction, executed:** authenticate a synthetic user; fake pricing with `tests/Fixtures/pricing.json`; POST `/generation-estimates` with `prompt = str_repeat('漢', 4000)`, square/low and no references; take the returned quote and POST the identical settings plus that quote to `/generations`. Estimate returns 200, quote is 44,344 characters, submit returns 422. Two thousand `🌅` characters gives the same result. Four thousand ASCII characters succeeds as a control. No provider request is needed for this reproduction.

**Related inspected limit:** native textarea `maxlength=4000` measures UTF-16 code units, while server/provider count Unicode characters. It limits supplementary characters sooner than the API contract. The 2,000-emoji reproduction already fits that native limit, so F01 does not depend on bypassing the browser restriction.

**Why tests missed it:** the 4,000-Unicode test calls the calculator directly. The request-level Unicode test uses only 400 emoji. Neither submits a maximum-sized valid encrypted quote.

**Recommended fix:** make the quote representation and its validation consistent with the maximum allowed payload. A small server-held quote identified by an authenticated token is an option; a deliberately bounded inline representation is also acceptable if its complete worst-case encoded size is supported. Do not just disable bounds or use an arbitrary larger number. Align frontend character counting with the API. Add full estimate→submit tests for 4,000 CJK characters, supplementary characters, JSON-escaped characters, and four maximum accepted URLs, plus too-long-input rejection.

### F02 — Medium: cooldown is not preserved across all retry paths

**References:** `app/Jobs/SyncGeneration.php:81–84`; `app/Http/Controllers/GenerationController.php:75–81`; `app/Actions/ApplyGeneration.php:67–71`; `tests/Feature/PixelforgeWorkflowTest.php:50–60`, :78–87; `tests/Feature/GenerationControllerTest.php:97–109`.

**Impact:** the app can contact the provider before its Retry-After deadline, wasting the account-wide request budget and prolonging throttling. Stable idempotency keys still protect against a new generation; no duplicate charge was observed.

**Reproduction A, executed:** start a generation at `sync_attempts=4`; return 429 `rate_limit_exceeded` with Retry-After 120. The fifth failure sets `next_sync_at=NULL`. Immediately POST its retry route and run its queued job: another provider request is sent without waiting. Existing tests cover active backoff and exhausted retries separately, not their intersection.

**Reproduction B, executed:** rate-limit retrieval of a processing generation with Retry-After 120. Apply a legitimate delayed `processing` snapshot for the same generation. `ApplyGeneration` resets next_sync_at to now+30 and attempts to zero, shortening the promised wait. Delayed lifecycle delivery is documented provider behavior.

**Recommended fix:** preserve a retry-not-before deadline independently from whether automatic retries are enabled. Manual resume and nonterminal snapshot application must not shorten it. Terminal settlement can clear scheduling. Test both interleavings with frozen time and assert no outbound request before the deadline. A shared account cooldown is worth considering for account-wide limits, without introducing a general scheduling framework.

### F03 — Medium: durable inbox recovery has a silent 24-hour cutoff

**References:** `app/Console/Commands/ReconcileGenerations.php:22–24`; `app/Jobs/ProcessWebhookEvent.php:14–20`; `app/Actions/ProcessWebhook.php:20–27`; `tests/Feature/ReconcileGenerationsTest.php:9–21`; `README.md:32–34`, :67.

**Impact:** an acknowledged, persisted event whose Redis dispatch is lost cannot recover through the documented scanner after 24 hours. Polling often compensates, so this is not a universal billing failure. If polling has paused or the provider is unavailable, a valid saved terminal event may remain unapplied indefinitely despite already existing locally.

**Reproduction, executed:** create an unprocessed inbox event with created_at 25 hours ago, fake the queue, invoke `pixelforge:reconcile`. No job is dispatched. The record remains unprocessed. The same query applies to generation events as to the diagnostic ping.

**Additional inspection concern:** the scanner repeatedly chooses the oldest 100 pending events. Permanently invalid snapshots can occupy that batch until they age out. Worker tries=3 does not bound scanner redispatch over the day. Batch starvation was not load-tested and is a code-supported scenario, not an observed incident.

**Recommended fix:** recover valid pending events regardless of creation age, with explicit next-attempt/backoff and quarantine/failed disposition for permanently invalid events so they cannot monopolize recovery. Keep the design proportional; an operator recovery command plus visible failed disposition can be sufficient. Add lost-dispatch-over-24-hours and poison-event/backlog tests. Do not silently mark malformed events processed to hide the issue.

### F04 — Medium: deletion promise contradicts actual data retention

**References:** `resources/js/components/DeleteUser.vue:29`, :62–67; `app/Http/Controllers/Settings/ProfileController.php:49–58`; `database/migrations/2026_11_17_172321_create_generations_table.php:14`, :17–29; `database/migrations/2026_11_17_172322_create_webhook_events_table.php:14`; `README.md:40`; `tests/Feature/Settings/ProfileUpdateTest.php:94–108`.

**Impact:** a user is told all resources/data will be permanently deleted, but prompts, references, generated-image URLs and financial records remain; webhook snapshots also have no user-deletion cleanup. Removing user_id is not the same as erasing potentially identifying prompt content. No claim about a particular legal violation is made.

**Reproduction, executed:** create a user with a generation; delete their account through the authenticated settings endpoint with the correct password. User disappears, generation remains, user_id becomes NULL, prompt is unchanged. Existing deletion test checks only user removal/logout.

**Recommended fix:** choose and explain a retention policy. Keeping minimal financial records may be reasonable; change the UI to state exactly what remains and evaluate redacting nonfinancial prompts/reference URLs/image URLs and webhook content. Preserve required settlement/reconciliation for in-flight requests. Add deletion-with-generation and deletion-during-processing tests before changing retention behavior.

### F05 — Medium: the end-to-end and concurrency claims exceed their test boundaries

**References:** `tests/Browser/ImageStudioTest.php:17–38`; `tests/Pest.php:23–37`; `tests/Integration/PixelforgeConcurrencyTest.php:11–38`; `tests/Feature/PixelforgeWebhookTest.php:30–39`; `AUDIT.md:59`.

**Impact:** the suite provides meaningful evidence but can stay green while important integration boundaries fail. This is a coverage/evidence defect, not a proved production settlement bug.

- The browser test directly invokes ApplyGeneration to change status. It verifies UI polling/rendering but bypasses webhook receipt, worker execution and provider polling for completion.
- It substitutes `favicon.svg` and asserts an image element is visible; it never checks successful decoding (`naturalWidth`) of an actual generated PNG. The fresh screenshot had an empty-looking image area at capture time; this alone does not prove a production rendering bug.
- The shared success fixture reports 6,450 output tokens and 765 reference tokens even for square/low/no-reference requests. The browser test consequently accepts a final charge of $0.3818875 against a same-rate maximum estimate of $0.0218375. That fixture is useful for standalone arithmetic but impossible for those submitted settings under the documented contract.
- The PostgreSQL test starts four independent processes and checks final amounts/event processing. This is useful. It pre-inserts inbox rows, lacks a barrier to force contention, and does not test concurrent HTTP inserts, conflicting states, worker termination, or create/poll/webhook overlap.
- The HTTP duplicate test asserts one inbox row and that a job was pushed, not a single push. Database/action idempotency, rather than job-count assertions, is the actual safety boundary.

**Recommended fix:** use contract-consistent scenario fixtures; add a focused browser completion flow through a signed webhook or the actual polling job with mocked provider HTTP; assert decoded image pixels, settings and maximum-vs-actual relationship at unchanged rates. Add deterministic contention tests at the inbox insert and generation settlement boundaries. Keep existing useful tests rather than replacing all coverage with an elaborate new rig.

### F06 — Low: paused and transient-error UI gives misleading recovery cues

**References:** `resources/js/pages/Dashboard.vue:395`, :405–422, :467–483; `app/Http/Controllers/GenerationController.php:33`; `resources/js/components/InputError.vue:8`; Dashboard:192, :201, :260.

**Impact, code inspection:** a paused request displays “We’ll keep checking” even though next_sync_at is NULL and no automatic check is scheduled. A single transient image error permanently hides that image for the mounted page and labels it unavailable/expired without distinguishing an unexpired URL. Validation errors are visible but not linked to inputs with error IDs/aria-describedby or aria-invalid; the prompt/reference descriptions point only to help text.

**Reproduction:** exhaust retries, view that card and compare the message to its retry button; block an otherwise valid image request once then restore network; trigger a field error and inspect accessible error association. Paused backend state was reproduced; these additional browser interactions were not separately automated in this review.

**Recommended fix:** derive paused copy from can_retry, offer an image retry/reload when appropriate, and associate field errors programmatically. Add focused browser checks. Do not call the passing critical/serious accessibility scan full accessibility certification.

### F07 — Low/context-dependent application risk; upstream High: picomatch advisory remains unresolved

**References:** `package-lock.json:3527` (4.0.7), :4223 (2.3.2); `vite.config.ts:9`, :30; `config/inertia.php:18–21`; `AUDIT.md:73`.

**Executed:** npm audit exits 1 with **14 high dependency entries**, not the historical 17. They trace to [GHSA-fc5q-39xc-vjpf / CVE-2026-112366](https://github.com/advisories/GHSA-fc5q-39xc-vjpf). **Recommended fix:** track a compatible upstream fix, keep development tooling private, and verify the actual production artifact/runtime excludes unnecessary Node tooling. Do not blindly apply npm's suggested major downgrade as proof of remediation. Re-audit before publication and document any explicit temporary risk acceptance. No dependency was changed or advisory suppressed here.

## 7. Security and billing assessment

### Supported protections

- **Exact arithmetic:** no floating-point monetary operations in the reviewed calculation/settlement/rendering path. Pricing's JSON variance arrives as a number but is converted to a decimal string before BCMath; currency rates and totals remain strings. Eighteen places cover the explicitly accepted rate/token/markup bounds.
- **Database invariants:** unique request/provider IDs and event primary key; CHECK constraints prohibit paid failed/pending records and enforce exact 1.25 multiplication. Settled NULL fields are explicitly rejected. Numeric columns alone would not provide these guarantees.
- **One settlement record:** row locking and terminal guards serialize results; there is no increment to apply twice. No mandatory balance feature exists.
- **Identity binding:** server-authenticated encrypted quotes bind user/settings/request key; snapshots must match metadata, provider ID once known and immutable parameters. Browser-supplied price/status are ignored.
- **Webhook boundary:** raw-body HMAC before decoding, constant-time comparison, timestamp window, 64-KiB body bound, strict envelope validation, inbox persistence before queue dispatch. CSRF exclusion is narrowly the provider route; user actions retain web middleware.
- **Safe uncertainty:** pre-POST marker survives an ambiguous submission; unknown outcomes are not converted to free terminal failures. Retries retain original parameters/key. Recognized provider errors use safe messages instead of raw error bodies.
- **Secrets:** no current API key, webhook secret or application key matched 303 tracked files, six reachable commits, or application logs. A private-key/AWS-key pattern scan of current tracked files also found no matches. `.env` is ignored and untracked. These scans cannot prove that no unknown historical credential exists anywhere.
- **Authorization:** user-scoped history, 404 ownership refusal on retry, hidden password/token user fields and explicit generation serialization. No attacker-controlled local fetch of reference images was found.

### Remaining security/financial limits

F02/F03 can delay reaching a correct financial state without corrupting arithmetic. Snapshot identity checks and terminal guards are sound under the documented immutable provider lifecycle; contradictory terminal events are ignored rather than creating a financial correction. Operators must investigate a genuinely contradictory provider result rather than relying on automatic reversal.

Replay prevention intentionally accepts a valid event within the timestamp window and deduplicates it by event ID. The implementation does not need to reject every repeated HTTP request to prevent duplicate effects. Unknown generation metadata returns false from ApplyGeneration and ProcessWebhook still marks that event processed (`app/Actions/ApplyGeneration.php:48–50`, `app/Actions/ProcessWebhook.php:25–27`). This is safe for irrelevant generations created outside this app, but provides no automatic rematching if a local record is later restored; that recovery scenario is untested.

No penetration test, dependency-source security proof, malicious browser payload matrix, live worker-kill experiment, or production proxy/cookie verification was performed. Session cookie defaults are HTTP-only and SameSite=Lax; deployment must set secure cookies and trustworthy HTTPS/proxy configuration (`config/session.php:172–202`, `README.md:65`). The local example's debug setting is deliberately local, not evidence that production is configured safely.
