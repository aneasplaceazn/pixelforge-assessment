## F08 fractional retry deadline remediation — 2026-11-18 UTC

**Discovery and impact.** A separately approved isolated request used the unchanged application client/job and a disposable local PostgreSQL database. It sent exactly one live `[overloaded]` POST: started **00:32:45.581407 UTC**, received **00:32:46.497845 UTC**, HTTP **503**, **Retry-After: 2**, persisted deadline **00:32:56 UTC**. Only these retry-related fields were captured. The observed 9.502155-second wait exceeded the provider's two-second requirement; no provider ID or local charge was recorded. No subsequent real provider request was permitted, so zero provider billing follows the documented overload rejection contract, not a separate fresh usage-ledger read. The disposable database and instrumentation were removed. This captures one new response, not the missing headers of the original five production attempts.

A subsequent **simulated-only** response exposed the defect: at **01:00:00.500000**, a 300-second header produced a persisted **01:05:00.000000** deadline and allowed a request 0.5 seconds early. Eloquent date serialization discards fractions; the existing `timestampTz` columns and model date format use whole seconds. Whole-second frozen tests had missed the boundary. This qualifies the earlier overload PASS: that observed production scenario respected its recorded deadlines, but the broader guarantee against early retries was not yet correct.

**Fix.** `app/Models/Generation.php::nextCheckAt()` now rounds a positive calculated delay upward with the installed Carbon 3.15.1 `ceilSecond()` API, then preserves whichever is later: that deadline or the existing `retry_not_before`. A timestamp already on a whole-second boundary gains no extra second. Zero-delay resumes remain immediately eligible when there is no future cooldown; they still preserve any active cooldown. The change adds four production-code lines. No schema, dependency, HTTP client, money calculation, request key, queue configuration or production data change is needed.

The reviewed flow is: `Client` parses the documented integer-seconds header → `SyncGeneration` chooses the maximum of provider delay and exponential backoff → the shared model helper rounds/preserves the deadline → the row-locked job refuses premature work. `GenerationController::retry`, `pixelforge:resume` and `ApplyGeneration` use the same helper. Scheduled recovery selects due work; a stale dispatch still encounters the independent cooldown guard. Terminal settlement clears cooldowns only when further provider work is unnecessary. Internal inbox retry scheduling and in-flight job reservations do not set provider cooldowns and were not changed.

**Regression evidence.** `tests/Feature/RetryDeadlineTest.php` adds 18 cases using real local PostgreSQL, actual client/job code, controlled HTTP responses and frozen clocks. They cover:

- `.000000`, `.000001`, `.500000` and `.999999` starts; headers 2, 120 and 300 seconds; literal expected persisted deadlines.
- No HTTP call one microsecond before the actual required delay or rounded deadline; calls permitted at the rounded deadline and later. A direct regression asserts no request at the previously truncated deadline.
- A later cooldown written while a request is in flight is retained by the row-locked failure handler.
- All five 10/20/40/80/160-second exponential delays, persistent final cooldown, automatic pause and stable idempotency keys.
- HTTP and operator-command resume after exhaustion, delayed signed processing webhooks, scheduler recovery and stale dispatched work.
- Immediate HTTP/CLI resume with no cooldown or an expired cooldown, plus unchanged zero billing on rejection and exact settlement after retrieval.

Before the fix, the initial 14 cases produced **12 failures / 2 passes, exit 1**, including an observed extra HTTP call at the truncated boundary. The first implementation rounded zero-delay resumes as well; the full suite caught two browser recovery failures (**160/162 passed, exit 1**). Four new focused cases reproduced that regression (**0/4 passed, exit 1**). Restricting rounding to positive delays fixed it. Three preexisting workflow tests now explicitly use `freezeSecond()` for their whole-second contracts; their assertions were preserved, and the new tests cover fractional starts. No test was skipped, deleted or weakened.

## Bonus implementation design — 2026-11-18 UTC (before implementation)

The following design is recorded before changing application behavior. The local F08 fix and its 166-test/932-assertion evidence remain the baseline, and existing uncommitted files have been copied privately outside Git for preservation.

- Credit accounts retain an opaque ID after user deletion. Append-only entries record fake purchases, reservations, settlement, release and payment of outstanding amounts. Available, reserved and outstanding USD are exact `numeric(30,18)`/BCMath sums, not independently editable balances. Account row locks serialize mutations; database triggers also lock and reject negative aggregates or mutation of ledger history. Unique constraints enforce purchase and generation-operation idempotency.
- The existing user lock serializes submissions and deletion. Settlement retains the existing event → generation ordering and then locks the credit account. Purchase locks user → account. Reservation creates a new generation inside the submission transaction before its account/ledger operation; no provider request precedes commit. Failure/cancellation releases reservations through the same terminal-finance operation.
- Existing generations have no reservation and are never charged retrospectively. Existing/new users begin with zero credits. Historical amounts remain reportable. No initial fake purchase or reviewer credit grant is automatic.
- Actual charge always remains exact provider cost plus 25%. Rates are fixed at provider acceptance, so pricing can change after quoting. On an overage, reserved and otherwise available credits cover as much as possible; the remainder is recorded as a nonnegative outstanding amount. Further reservations are blocked until it is paid. Explicit fake purchases pay outstanding amounts first. No provider cost or charge is silently capped, and available credits never become negative.
- Operator privileges default false, are excluded from registration/mass assignment, and are granted/revoked for existing users only by a CLI command. Authorization guards the routes and reporting service. Shared props contain no cross-user financial data.
- Reports use settled generation records and UTC provider-completion dates, including late arrivals and anonymized historical records. Pending records are shown separately. `/usage` comparisons preserve nine-decimal provider values and compare exactly at storage precision without financial rewrites. The documented list endpoint is account-scoped, whereas usage is key-scoped: scoped metadata/known local identities can support individual discrepancy identification, but unidentifiable key scope or incomplete scans must remain explicitly unverified rather than fabricated.
- No new dependencies, real payments, infrastructure, hosted mutation, push, deployment or provider generation is authorized for implementation. Fresh/upgrade migrations and real PostgreSQL contention tests will run locally before any readiness verdict.

**Bonus design refinement (before final verification):** credit purchases and returned reservations both pay any existing outstanding charge before becoming spendable. Each payment is a separate immutable entry linked to its purchase or release. A failed generation still has zero charge; its full reservation is released, and any subsequent debt payment pays an earlier successful generation. This prevents a stranded available balance while outstanding charges block new work.

### Redis deadline and deferral behavior

`ProviderCooldown::{deadline,extend,key}` stores one scalar epoch second per account or read endpoint. `ceilSecond()` retains F08 upward rounding; the Lua operation reads the existing deadline and writes the maximum plus its remaining TTL atomically, without a time-limited application lock lease. A malformed scalar is not interpreted as “no cooldown”: the client fails closed. Redis transport/configuration failure before send also returns a local deferral without a provider request. Actual HTTP errors continue to count toward bounded retries; a request that never left the application does not consume that budget. Existing later generation deadlines and longer exponential backoffs still win.

Configuration uses `PIXELFORGE_COOLDOWN_CONNECTION=cache` (existing Redis connection) and `PIXELFORGE_ACCOUNT_SCOPE=primary` (a non-secret operator-selected label). The key includes provider base URL and that label, not the API key. Tests give each case a unique synthetic label to avoid cross-test state; real integration children deliberately share it. Production/default operation always uses Redis for this guard even if the general cache driver is changed. It is not an array-store simulation.

Coordination requires the same Redis server/database/prefix, base URL and account label across clients. Different keys on the same configured account share the pause. Separate installations/stores and clients that bypass this application cannot coordinate through this record. UTC clocks must agree. Keep the existing noeviction policy and persistent Redis state; reconnect retaining state passed, but server restart/failover/data loss was not induced on shared development services. If a deadline cannot be persisted because Redis fails, this implementation cannot promise that an independent client later reconstructs the lost observation. Do not flush the store or change prefixes/account labels during a live cooldown. No new replica/service is required.

The client checks immediately before HTTP as well as before its local request budget. Another response can establish a limit after a concurrent request has passed its check; that already-admitted/in-flight request cannot be withdrawn. The contention test intentionally models this and verifies that both responses preserve the longest subsequent pause. It does not claim globally serialized network I/O.
